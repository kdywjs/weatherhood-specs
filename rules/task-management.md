# 작업 및 일정 관리

프로젝트의 진행상황, 담당 작업, 일정과 작업 상태는 [Weatherhood GitHub Project](https://github.com/orgs/kdywjs/projects/1/views/1)에서 관리한다.

## GitHub Issue

- 진행할 작업은 작업 대상 레포의 Issue로 만들고 GitHub Project에 추가한다. 공통 문서·스펙·테스트 설계 작업은 `weatherhood-specs`, 앱과 서버 구현 작업은 각각 해당 레포에 등록한다.
- Issue에는 작업 목적, 상세 내용, 논의와 결과물 링크를 기록한다.
- Project에 별도 항목을 중복 생성하지 않고 같은 Issue를 연결한다. 초안 항목으로 시작한 작업은 진행할 때 해당 레포의 Issue로 전환한다.

## 이슈 양식과 카테고리

- 세 레포의 `.github/ISSUE_TEMPLATE/`에서 기능, 버그, 설계, 테스트, 문서·협업 도구, 유지보수 양식을 제공한다. 양식을 선택하면 같은 이름의 라벨을 적용한다. 빈 이슈 작성도 허용한다.
- 필수 항목은 기능의 목적·필요한 동작, 버그의 문제 현상·기대 동작, 설계의 설계 목적·결정할 사항, 테스트의 검증 대상·확인할 상황, 문서·협업 도구의 변경 목적·변경할 내용, 유지보수의 현재 문제·정비할 내용이다.
- 관련 스펙·자료, 제약, 제외 범위는 선택이다. 버그의 재현 방법과 실행 환경·첨부 자료도 선택이다.
- 상세 요구사항과 설계는 스펙 문서에서 관리하고 Issue에서 연결한다. 별도 스펙이 필요 없는 작은 작업은 Issue만으로 설명할 수 있다. 테스트를 위한 설계는 테스트, 구현 방향을 정하는 설계는 설계로 분류한다.

## Pull Request

- 각 레포의 `.github/pull_request_template.md`에 따라 연결된 이슈, 변경 내용과 이유, 검증 방법과 결과를 작성한다. 검증하지 않았다면 이유를 적는다. 검토 요청 사항은 선택이다.
- 연결만 하는 이슈는 `Refs #번호`, 완료하는 이슈는 `Closes #번호`로 표시한다. 다른 레포는 `owner/repo#번호`로 지정한다. 자동 종료는 기본 브랜치에 머지될 때 적용된다.
- 한 이슈를 여러 PR로 진행하거나 여러 이슈를 한 PR에 연결할 수 있다. 완료하지 않은 이슈에 종료 키워드를 사용하지 않는다.
- 담당자, 우선순위, 일정과 상태는 Project에서 관리하며 양식에 중복 입력하지 않는다.

## GitHub Project

- 각 담당자가 현재 진행하는 작업의 Issue를 연결한다.
- 담당자, 우선순위, 시작일과 목표일을 작업에 맞춰 설정한다.
- 작업의 진행상황과 상태를 변경사항에 맞춰 갱신한다.
- 일정이 정해진 작업은 해당 일정을 기록한다.
- 관련 스펙, PR과 결과물은 연결된 Issue에 기록한다.

## 기능 스펙의 tasks.md

- 기능 구현에 필요한 작업 분해, 의존 관계와 검증 항목을 기록한다.
- 담당자, 일정과 현재 진행 상태의 기준은 GitHub Project에 둔다.
- 관련 Project 항목을 참조해 진행상황을 중복 관리하지 않는다.
