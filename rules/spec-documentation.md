# 스펙 문서 작성

스펙 문서는 기능의 현재 기준을 읽고 구현·검증할 수 있는 원본이다. 작업 일지나 날짜별 변경 기록으로 작성하지 않는다.

## 문서 책임과 원본 위치

이 기준은 모든 기능과 앱·서버 레포의 문서 작성·수정·리뷰에 적용한다.

| 내용 | 원본 위치 |
| --- | --- |
| 제품 목적·범위, 사용자 동작·예외·수용 기준 | 스펙 레포 `docs/`, `specs/<기능>/requirements.md` |
| 기능 전체 설계: 화면 동작, 앱·서버 책임, 데이터 흐름, 외부 연동, 기능별 DB·검색·처리 구조 | 스펙 레포 `specs/<기능>/design.md` |
| API 경로·요청·응답·오류, 인증 계약, 공유 데이터 형식 | 스펙 레포 `contracts/` |
| 기능별 작업 분해·의존 관계·검증 항목 | 스펙 레포 `specs/<기능>/app-tasks.md`, `specs/<기능>/server-tasks.md` |
| 플랫폼 공통 기술 스택·버전과 선택 이유, 공통 패키지 구조 | 해당 앱·서버 코드 레포의 `docs/` |
| 실행·설정·테스트·배포·운영 절차와 구현 검증 증적 | 해당 코드 레포의 `README.md`, `docs/` |
| 팀 전체에 적용할 작업 규칙 | 스펙 레포 `rules/` |

- 기능 문서는 플랫폼보다 기능을 기준으로 모은다. 요구사항과 앱·서버 구현 설계의 원본은 스펙 레포의 같은 기능 폴더에 둔다. `specs/app/`, `specs/server/` 또는 코드 레포의 별도 기능 스펙으로 분산하지 않는다.
- 예: ‘사용자별 저장 지역과 순서를 유지한다’는 기능 요구사항, 요청·응답 필드는 API 계약, PostgreSQL·JPA 등 서버 공통 기술 선택은 서버 문서, 기능별 테이블·인덱스와 카카오 연동은 기능의 `design.md`다.
- 예: 사용자에게 제공할 날씨 기간·오래된 자료 표시·누락 처리 기준은 공통 스펙, 이를 구현하는 수집 작업·저장 최적화·재시도 설계는 기능의 `design.md`다. 실제 코드·마이그레이션·자동 테스트는 코드 레포에 둔다.
- 같은 설명을 양쪽에 복사하지 않는다. 다른 레포에는 필요한 요약과 원본 링크만 둔다. 통합 작업 공간에서는 상대 경로로 연결할 수 있다.
- 구현 변경이 공통 동작이나 API 계약을 바꾸면 관련 스펙의 합의·수정도 함께 한다. 기능 내부 설계가 바뀌면 해당 기능의 `design.md`를 갱신하고, 플랫폼 공통 구조나 실행·운영 방식 변경은 코드 레포 문서를 갱신한다.
- 기존 문서를 수정할 때도 이 기준을 적용해 잘못 놓인 내용을 원본 위치로 옮기고 참조를 갱신한다. 삭제된 구현의 검증 결과를 현재 구현의 증적으로 사용하지 않는다.

## 본문

- `requirements.md`에는 목적·범위·현재 요구사항·예외·미정 사항·수용 기준을 쓴다.
- `design.md`에는 현재 화면 구성·상태·데이터 흐름·설계 제약과 기능별 구현 설계를 쓴다. 공통 흐름, 앱 설계, 서버 설계를 필요한 만큼 구분하며 API 계약은 링크로 참조한다.
- `app-tasks.md`와 `server-tasks.md`에는 각각의 구현 작업·테스트 항목·선행 조건과 Issue·PR·Project 링크를 쓴다. 같은 요구사항을 다시 정의하지 않는다. 플랫폼 간 의존 작업은 상대 작업 문서를 참조한다. 진행 상태·담당자·일정은 Project에서 관리한다.
- 해당 플랫폼 작업이 없으면 작업 문서에 범위 없음과 근거를 짧게 명시한다. 미정인 작업을 임의로 확정하지 않는다.
- 합의가 바뀌면 해당 본문을 현재 기준으로 고친다. `날짜: 수정 승인`, `기존에는… 이후에는…` 같은 변경 이력을 중간에 추가하지 않는다.
- 미정인 사항은 미정으로 표시한다. 시안이 존재하거나 사용자 화면 합의가 있다고 팀 전체 MVP·데이터 계약·구현 완료로 간주하지 않는다.

## 문서 끝의 참고 및 검증

- 시안 링크·참고 자료·승인 근거·검증 방법과 결과·증적 링크는 마지막 `참고 및 검증`에 모은다.
- 요구사항 문서에서 설계 문서의 증적을 참조하고 같은 검증 기록을 반복하지 않는다.
- 날짜가 근거에 필요하면 이 마지막 항목에 둔다. 기능 자체에 필요한 시간·예보 기간 등은 본문에 쓴다.
- 실제 수행한 검증과 확인하지 못한 동작을 구분한다. 정적 시안 확인을 앱 동작 검증으로 표현하지 않는다.
- 이전 시안은 비교 자료로 표시하며 현재 스펙과 충돌하면 본문이 기준임을 명시한다.
- 상세 변경 이력과 논의 경과는 Git·Issue·PR에서 관리한다. 스펙에는 최신 기준을 통합한다.

## 수정 후 확인

본문만 읽어 현재 동작과 미정 사항을 이해할 수 있는지, 이전 기준과 새 기준이 함께 남아 있지 않은지, 증적이 마지막에 모여 있는지 확인한다.
