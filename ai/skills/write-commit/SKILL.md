# 커밋 작성

이 지침은 2026-10-11, 스펙 레포 커밋 `d66db4ea633e9b2812d644ace994f1dafc00338d`의 `rules/commit.md`를 기준으로 한다. 일반 실행 시 기준 파일을 다시 읽을 필요는 없다. 사용자가 규칙 변경을 알리거나 갱신을 요청하면 현재 규칙과 비교하고 이 스킬과 설명 문서의 기준 정보를 함께 갱신한다.

## 메시지 양식

```text
<type>(<scope>): <변경 내용>

<변경한 이유나 주요 영향>

Refs #<이슈 번호>
```

- 제목은 필수이며 변경 내용을 한글로 간결하게 작성한다.
- scope는 기능이나 폴더 등 변경 영역이 명확할 때만 짧게 적고, 여러 영역에 걸치면 생략한다. 분리된 레포 이름 app·server·specs를 반복할 필요는 없다.
- 본문은 제목만으로 부족할 때 이유·영향·주의점을 적는다. 제목과 본문 사이에 빈 줄을 둔다.
- 이슈 참조는 선택이다. 관련 이슈가 있으면 `Refs #번호`, 다른 레포는 `Refs owner/repo#번호`를 사용한다. 이슈 종료는 PR에서 결정한다.

| type | 용도 |
| --- | --- |
| feat | 기능 추가 |
| fix | 버그 수정 |
| docs | 문서 변경 |
| test | 테스트 추가·수정 |
| refactor | 기능 동작을 유지하는 코드 구조 변경 |
| style | 공백·포맷 등 코드 의미에 영향 없는 변경 |
| build | 빌드 설정·의존성 변경 |
| ci | CI 설정 변경 |
| perf | 성능 개선 |
| chore | 위 분류에 해당하지 않는 관리 작업 |
| revert | 이전 커밋 되돌리기 |

예시: `docs(rules): 커밋 메시지 규칙 추가`

## 실행

1. 대상 레포, 브랜치, Git 상태와 실제 diff를 확인한다. 상위 통합 작업 공간은 Git 레포가 아니므로 app·server·specs별로 수행한다.
2. 메시지 작성만 요청했다면 메시지만 제공한다. 커밋 실행이 요청됐다면 요청한 변경만 포함한다. 기존 스테이징과 관련 없는 변경은 보존한다. 같은 파일에 다른 작업이 섞여 분리하기 어렵거나 범위가 불명확하면 확인한다.
3. 변경에 필요한 검증을 수행하고 결과를 확인한다. `git diff --cached --check`로 스테이징된 변경을 점검한다. 실패한 검증은 숨기지 않는다.
4. 위 양식으로 실제 변경을 설명하고, 대상 파일 또는 관련 부분만 스테이징해 비대화형 커밋을 만든다. 여러 줄 메시지는 UTF-8 임시 파일과 `git commit -F`를 사용한다.
5. 커밋 결과와 남은 변경을 확인한다. 푸시를 명시적으로 요청받았을 때만 대상 원격·브랜치를 확인해 푸시한다. 강제 푸시나 amend는 별도 요청 없이 수행하지 않는다.
6. 커밋 해시·제목, 검증 결과, 푸시 여부와 남은 작업을 보고한다.
