# 문의하기 설계

## 현재 구성과 흐름
마이의 기존 `문의하기` 행을 진입점으로 사용한다. 별도 문의 페이지·입력 폼을 추가하지 않는다.

1. 사용자가 마이의 문의하기를 선택한다.
2. 주소와 연결 정책 확정 후 앱이 OS의 이메일 작성 연결을 요청한다.
3. 이메일 작성 UI는 OS 또는 외부 이메일 앱이 제공한다. Weatherhood가 해당 UI를 제작하거나 소유하는 화면처럼 표현하지 않는다.

앱은 문의 접수 상태를 저장하거나 서버에 전달하지 않는다. 이메일 앱 열기와 문의 전송·접수는 구분한다.

## 상태와 문구

| 상태 | 현재 기준 |
| --- | --- |
| 마이 | 기존 문의하기 행을 사용한다. |
| 수신 주소 미정 | 연결 구현과 실제 실패 안내를 확정할 수 없다. 임의 주소·실행 가능한 메일 링크를 만들지 않는다. 사용자에게 보여 줄 동작과 문구는 미정이다. |
| 이메일 작성 연결 | OS·외부 앱 영역으로 위임한다. 호출 방식과 지원 플랫폼별 동작은 미정이다. |
| 이메일 열기 실패 | 안내 형식·문구·실패 판단 방식은 미정이다. 주소 표시와 복사 버튼은 검토 제안이다. |
| 작성 취소·복귀 | 전송·접수 완료를 표시하지 않는다. 플랫폼별 복귀 동작은 확인이 필요하다. |

검토 제안은 제목 `웨더후드 문의`, 사용자의 본문 작성과 직접 전송, 열기 실패 시 확정된 수신 주소와 `복사` 버튼이다. 제목 사전 입력·복사 결과 안내를 포함한 세부 동작은 합의 후 반영한다.

## 설계 제약과 책임
- 수신 주소 확정이 이메일 연결 구현의 선행 조건이다. 메일 연결 방식과 실패 처리 정책도 결정해야 한다.
- 지원 서버·API·앱 내 문의 폼·접수 완료 화면을 추가하지 않는다.
- 이번 준비에서는 이메일을 실제 전송하지 않는다.
- 검토용 시안이 필요해져도 외부 메일 작성 UI를 Weatherhood 화면처럼 제작하지 않는다.

## 마이페이지 연동
마이페이지의 문의하기 행은 이메일 작성 연결 진입점이다. 수신 주소와 세부 연결·예외 정책은 이 기능에서 관리하고 마이는 이를 참조한다. 문의 하위 화면을 별도로 추가하지 않는다.

## 참고 및 검증
- 진입점 원본: [마이페이지 설계](../my-page/design.md), 요구사항 원본: [requirements.md](requirements.md).
- 작성 기준: [스펙 문서 작성 규칙](../../rules/spec-documentation.md).
- 정적 문서 확인: 확정 범위와 미확정 제안을 분리하고, 주소 미정 제한·제외 범위·마이 연동 수정 필요 항목을 확인했다.
- 브라우저·Figma는 사용하지 않았다. 추가 화면이 필요하지 않고 실패 안내가 미정이므로 검토용 JSON은 생성하지 않았다.
- 앱 구현·실기기 메일 연결·실패 안내·복사·취소·복귀는 검증하지 않았다. 실제 이메일 전송은 수행하지 않았다.
- 마이 요구사항·설계·작업에서 이메일 연결을 참조하도록 연동했다. [마이 시안](https://www.figma.com/design/nIUPdpIqFoqtPBCBPwOJ3N?node-id=144-250)의 문의하기는 정적 메뉴이며 실제 외부 연결은 미검증이다.
