# 지역별 날씨 데이터 설계

요구사항 원본: [requirements.md](requirements.md). 계약 원본: [날씨 API](../../contracts/weather-api.md).

## 흐름과 책임
앱 → Weatherhood 조회 API → 공유 저장 자료 조회 → 필요한 기상청 자료 수집·검증·저장 → 응답 조합 순서다. 서버 내부 기술 선택·구조·테스트 기준은 [서버 설계](../../../weatherhood-server/docs/architecture.md)를 따른다.

서버는 인증키, 좌표 변환, 공급처 발표 시각 계산, 결측 및 코드 정규화, 수집·저장·재시도와 출처를 관리한다. 앱은 선택 지역·날짜·시각·재생·단위 표시, 날씨 상태에 따른 캐릭터·배경·아이콘을 관리한다. 데이터 새로고침 시 선택 시각의 수치와 장면을 같은 응답 기준으로 함께 교체한다.

## 공급 자료
| 용도 | 기상청 후보 | 제약 |
| --- | --- | --- |
| 현재 실황 | `VilageFcstInfoService_2.0/getUltraSrtNcst` | 하늘상태가 없어 해당 시각 예보로 보충한다. |
| 가까운 시간 | `VilageFcstInfoService_2.0/getUltraSrtFcst` | 실제 대상 시간·발표 및 제공 지연을 확인한다. |
| 시간별 예보 | `VilageFcstInfoService_2.0/getVilageFcst` | 제공 기간·연장 구간·미만/범위 값을 실제 응답에서 확인한다. |
| 중기 요약 | 중기 육상예보·기온예보 | 서로 다른 지역 코드와 반일/일별 자료를 연결한다. |
| 오늘 지난 시간 | 시간별 실황 재조회와 저장 자료 | 초기 기동과 신규 지역의 00시부터 복구 가능 여부를 확인한다. |

오늘의 과거 구간을 확보하는 공급 경로는 구현 전에 실제 조회로 검증한다. `getUltraSrtNcst`의 소급 범위가 부족하면 API허브의 시각 지정 격자 실황을 검토한다. ASOS/AWS를 사용할 경우 관측소 좌표와 예보 격자가 다르므로 대표 지점·거리·결측 정책을 먼저 정한다. 가장 가까운 관측소 값을 같은 위치의 실황인 것처럼 대입하지 않는다.

예보로 과거 값을 보충할 경우 해당 대상 시각 이전에 발표된 예보를 사용하고, 대상 시각 이후에 발표된 자료를 당시 예보로 표시하지 않는다. 해당 시간의 실황·예보 모두 없으면 누락 구간이다. 전체 기간 확보가 안 되는 구현은 첫 수용 기준을 통과한 것으로 보지 않는다.

## 수집·저장의 공통 동작
- 같은 격자의 자료를 요청 간 공유하고 일부 수집 실패가 정상 저장 자료를 훼손하지 않도록 한다.
- 저장 자료가 충분하면 조회에 사용한다. 자료가 부족할 때의 대기·부분 응답·실패 기준은 API 계약에서 결정한다.
- 기존 요구사항의 최소 48시간 보존과 현재 유효한 미래 예보 제공 범위를 만족해야 한다. 실제 공급처에서 확보할 수 있는 자료와 소급 범위는 검증한다.
- 발표·갱신 실패·오래된 자료·결측 여부를 API에서 구분할 수 있어야 한다. 인증키와 정확한 사용자 좌표를 로그에 노출하지 않는다.
- 수집 키·동시 작업 합치기·페이지 검증·갱신 작업 등 내부 구현 설계는 [서버 날씨 수집 설계](../../../weatherhood-server/docs/weather-data.md)에서 관리한다.

## 시간과 조합
현재 요약은 실제 현재 시각을 기준으로 조합하며 선택 날짜의 시각과 분리한다. 지난 구간의 실황과 미래 구간의 예보는 동일한 시간대·단위의 점 자료로 정리한다.

기온은 해당 시각의 값이고 강수량은 특정 기간의 누적이다. 대상 시각이 같다는 이유로 집계 기간이 다른 강수량을 합치거나 중복 합산하지 않는다. 1시간·3시간 등 간격은 응답에 남기며 분 단위 탐색이 분 단위 예측 정확도를 의미하지 않는다.

날짜별 요약의 대표 날씨·최고/최저는 공급처 자료를 사용하고 집계 근거를 남긴다. 최초 구현에서 계산 규칙이 정해지지 않은 대표 날씨나 총 강수량은 임의 산출하지 않는다. 중기 자료만 있는 날짜는 시간별 탐색 불가를 명시한다.

## 예외와 미정
계약의 `complete`·`partial`·`stale`과 오류 코드를 사용한다. 오래된 부분 자료는 `stale`과 누락 목록을 함께 제공한다. 공급처 제한 시 실패 요청을 사용자 수만큼 반복하지 않는다.

오래된 자료의 최대 나이, 재시도 시간 예산과 횟수, 최근 지역의 유지 기간, 부분 응답으로 제공할 최소 핵심 데이터는 실제 응답을 확인한 뒤 결정한다. 구현 시 이 값을 숨은 기본값으로 확정하지 않는다.

- 공식 이용안내는 일반회원 일 20,000건·5GB이며 시스템 상황에 따라 바뀔 수 있다고 안내한다. 인증 계정의 실제 한도를 수집 예산에 적용한다.
- 기존 프론트 참고: `weatherhood-app`의 로컬 추적 브랜치 `origin/codex/urban-weather-main`, 커밋 `30dd6e4`, `Weatherhood/MainWeatherState.swift`. 7일 가상 데이터·샘플 시계·고정 일출 구간은 공급 계약으로 채택하지 않았다.
- README·기능 문서·계약 등 관련 Markdown 8개, 로컬 링크 19개와 예시 JSON 1개의 파싱·시각 오프셋·점 정렬/중복 여부를 확인했다. `git diff --check`에서 공백 오류가 없었다. 이는 계약 예시 확인이며 서버 구현 테스트가 아니다.
- 서버 구현은 초기화되었다. 초기화 이전의 테스트·빌드 기록은 Git 이력에 있으며 현재 설계의 구현 검증 증적으로 사용하지 않는다. 새 서버의 구현·테스트 결과는 서버 레포에서 관리한다.
- 인증키를 사용한 실제 기상청 조회와 앱·실기기 동작은 미검증이다. 중기예보·부가 지표 공급 연결과 운영 정책은 남아 있으며 실제 한 지역의 날씨 제공을 완료 처리하지 않았다.
