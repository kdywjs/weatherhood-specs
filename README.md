# Weatherhood Specs

Weatherhood의 제품 문서, 기능 스펙, 앱·서버 계약, 팀 규칙과 AI 작업 절차를 관리합니다. 현재는 구조와 문서 책임만 정의한 초기 뼈대입니다. 세부 내용은 팀과 합의하며 추가합니다.

## 구조

```text
weatherhood-specs/
├── README.md       --- 문서 지도와 관리 책임
├── docs/           --- 제품 목표·범위·용어와 시스템 전체 구조
├── specs/          --- 기능별 요구사항·설계·작업
├── contracts/      --- 앱·서버가 공유하는 인터페이스의 원본
├── rules/          --- 사람과 AI가 함께 따르는 팀 공통 작업 규칙
└── ai/
    ├── AGENTS.md   --- 로컬 통합 작업 공간 지침의 원본
    └── skills/     --- 합의된 반복 작업 절차와 실행 도구
```

## 문서 위치

| 내용 | 위치 |
| --- | --- |
| 제품 목표, 대상 사용자, MVP 범위, 공통 용어 | `docs/` |
| 앱·서버·외부 서비스의 역할과 공통 설계 결정 | `docs/` |
| 기능의 동작과 수용 기준 | `specs/<기능>/requirements.md` |
| 기능의 화면 상태, 데이터 흐름, 앱·서버 책임 분담 | `specs/<기능>/design.md` |
| 기능 구현 작업, 의존 관계, 검증 항목, Issue·PR 참조 | `specs/<기능>/tasks.md` |
| 공통 API 요청·응답·오류 및 데이터 형식 | `contracts/` |
| 공통 개발 규칙, 코드 컨벤션, 변경 확인·문서 동기화 규칙 | `rules/` |
| AI 공통 작업 지침과 반복 작업 절차 | `ai/` |
| 앱 또는 서버 내부 구조, 전용 컨벤션, 실행·테스트 방법 | 해당 코드 레포 |

같은 내용은 한 곳에서 원본을 관리하고 다른 문서에서 참조합니다. 디자인 링크와 참고 자료는 관련 제품 문서 또는 기능 설계에 연결합니다. 기존 와이어프레임은 합의된 요구사항과 구분합니다.

## 기능 스펙

`specs/`의 폴더 하나는 독립적으로 설명하고 검증할 수 있는 사용자 기능을 나타냅니다. 화면 하나나 API 하나를 반드시 폴더 하나로 만들지는 않습니다.

```text
specs/<기능>/
├── requirements.md --- 무엇·왜·제약·제외 범위·예외 동작·수용 기준
├── design.md       --- 요구사항을 구현하는 방법과 설계 이유
└── tasks.md        --- 구현 작업과 검증 항목
```

실제 기능을 정의할 때 세 문서를 만듭니다. 작성·수정 전에 [스펙 문서 작성 규칙](rules/spec-documentation.md)을 읽습니다. 본문은 기능의 현재 기준으로 통합하고, 참고 자료·승인 근거·검증 증적은 마지막에 모읍니다. 변경 이력과 논의 경과는 Git·Issue·PR에서 관리합니다.

## 로컬 작업 공간

```text
weatherhood/
├── AGENTS.md              --- ai/AGENTS.md에서 가져온 사본
├── weatherhood-specs/     --- 이 레포
├── weatherhood-app/       --- 앱 코드 레포
└── weatherhood-server/    --- 서버 코드 레포
```

상위 폴더는 Git 레포가 아닌 통합 작업 공간입니다. 각 레포의 브랜치·커밋·PR은 별도로 관리합니다.

공통 지침의 원본은 `ai/AGENTS.md`이며 루트 사본을 바꿀 때는 원본도 함께 반영합니다. 자동 동기화 방식과 실행 주기는 아직 정하지 않았습니다.

## 앞으로 합의할 내용

팀 개발 절차, 테스트 방식, 다른 담당자의 확인이 필요한 변경 범위, 문서 동기화 정책은 아직 미정입니다. 규칙은 합의 후 `rules/`에 추가하고, 반복 실행이 필요하면 `ai/skills/`에 절차를 추가합니다. 빈 폴더의 `.gitkeep`은 Git 추적을 위한 파일입니다.
